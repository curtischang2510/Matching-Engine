# V3 — ITCH / MoldUDP release

V3 forks from V2 (see `MINI_VERSION_HISTORY.md` for V2's own history) but changes what each side of the system *is*. This is a bigger structural change than V1→V2, so it gets its own top-level version rather than another mini-version bump inside V2.

## What changed and why

Reading through V2's actual code made something clear: the C++ program (`Exchange` + `OrderBook` + `TcpServer`, receiving orders and matching them) has always behaved like an exchange's matching engine, while the Python `market_data_feeder` has always behaved like a client submitting order flow into it. Neither side was ever named for what it does.

V3 keeps that same wire relationship but gives each side an honest name and a real job to grow into:

- **`exchange/`** (Python, this directory) — was `market_data_feeder`. Its role stays "generates order flow," but it also becomes the side that will **emit market data as ITCH messages over MoldUDP64** — the reliable UDP session protocol real exchanges use to publish order-by-order book updates. Python is the right side for this: it doesn't need to be low-latency, it just needs to be correct and easy to iterate on while the wire format is still being worked out.
- **`MarketMaker`** (C++, this directory's root — CMake target renamed from `OrderBook`) — was the matching engine. Its role changes to **consuming** that ITCH/MoldUDP feed, maintaining its own local view of the book, and eventually deciding what to do about it. C++ is the right side for this because the consume-and-react loop is the latency-critical path — which is exactly what V2's whole optimization track (`CircularBuffer`, `StockTicker` enum, async logging) was already oriented toward.

This also resolves an open question from earlier: whether this project is building an L2 or L3 book. Real ITCH is order-by-order (L3) — `Executed`/`Cancel`/`Delete` messages reference a specific resting order by its order ID, not just "the next thing in FIFO order at this price." So both sides of V3 need an order ID that survives from the moment `exchange/` assigns it through to the moment `MarketMaker` looks it up.

**Scope note:** this release is the structural move (fork, rename, spec) plus the two protocol pieces below. The actual MoldUDP64 encoder/decoder, the ITCH message parser, and the order-ID-indexed book are being built by hand from here, not generated by this pass.

**Out of scope for now:** the strategy engine (what `MarketMaker` decides to quote/do once it has a local book) is explicitly not part of this project at this stage. The current focus is the feed and book-reconstruction plumbing — ITCH/MoldUDP64 and order-ID indexing — not the decision-making layer on top of it.

## Reference: MoldUDP64 packet layout

Real NASDAQ MoldUDP64 packet, sent over UDP (normally multicast; a single unicast socket on localhost is enough for this project):

```
Session (10 bytes)         identifies this feed session
Sequence Number (8 bytes)  sequence number of the FIRST message in this packet
Message Count (2 bytes)    how many messages follow (0 = heartbeat, no payload)
  Message 1: [2-byte length][payload bytes]
  Message 2: [2-byte length][payload bytes]
  ...
```

Reliability comes from the sequence number: a receiver tracks "next expected sequence" and can detect a gap immediately. Real MoldUDP64 recovers gaps via a separate retransmission-request service — worth treating as a stretch goal rather than day-one scope, since UDP delivery on localhost rarely drops anything and the framing itself is the part worth getting right first.

## Reference: ITCH message subset

Real ITCH 5.0 has ~20 message types; only these are needed to reconstruct a displayed, order-by-order book:

| Message | Carries | Effect on the book |
|---|---|---|
| Add Order | order ID, side, price, shares | new resting order enters |
| Order Executed | order ID, executed shares | reduces (or, if it reaches zero, implicitly removes) the resting order |
| Order Cancel | order ID, canceled shares | partial reduction of a resting order |
| Order Delete | order ID | full removal of a resting order |
| Order Replace | old order ID, new order ID, new price/shares | atomic cancel-old + add-new — the fiddliest one, worth building last |

Not needed for a displayed-book reconstruction: Add Order w/ MPID (attribution only), Order Executed With Price (hidden/cross executions), Trade/non-cross (hidden liquidity), System Event, Stock Directory, and any auction/circuit-breaker messages.

One real-ITCH behavior worth preserving deliberately: when `Executed`/`Cancel` brings a resting order to zero remaining shares, no separate `Delete` is sent — removal is implicit. Whatever indexes orders by ID needs to detect and handle that itself.

## Design questions — order-ID indexing

Left open on purpose. Some things worth deciding before writing the index:

- Who assigns the order ID — `exchange/` at Add time (most realistic, matches how a real exchange stamps an order reference number on acceptance) or something else?
- What's the ID's type and lifetime — dense/reusable, or monotonic and never reused? Reuse is more realistic but adds a "is this ID currently live" question; monotonic is simpler but you have gaps if the exchange fabricates one per real ITCH implementation each trading day.
- On the consuming side: a resting order needs to be found by ID (for `Executed`/`Cancel`/`Delete`) *and* by price-time position (for book/L1/L2 queries and for matching-adjacent reasoning). That's two access patterns over the same data — worth sketching both before picking a container shape, rather than defaulting to "a map of IDs" and discovering the price-ordering problem later.
- Does the index need to survive a session restart (MoldUDP64's Session field exists in real systems partly for this), or is a fresh index per run acceptable for now?

## What already exists vs. what's still a stub

| Piece | Status in this release |
|---|---|
| `exchange/` Python package | Copied from `market_data_feeder`, renamed (`market_data_feeder.py` → `exchange.py`, `MarketDataFeeder` → `Exchange`). Still sends plain protobuf `Order` messages over TCP — ITCH/MoldUDP64 encoding is not implemented yet. |
| `MarketMaker` C++ target | Copied from V2's `OrderBook` target, CMake target renamed only. `OrderBook.h`/`OrderBook.cpp` and the `Exchange` class inside them still carry their V2 names and V2 behavior (bare-quantity FIFO per price level, no order ID) — **not yet renamed or restructured**. That refactor (order-ID-keyed storage, whatever the new class ends up being called) is intentionally left for the next pass. |

| ITCH message parser/encoder | Not implemented on either side |
| Order-ID indexing | Not implemented — see design questions above |
